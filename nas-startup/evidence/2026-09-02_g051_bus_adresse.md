# `G-051`: Die Bus-Adresse zeigte auf nichts

**2026-09-02, gemessen, nicht geschlossen.** Gefunden beim Vorbereiten des
Phase-5-Fensters, beim Lesen von `compose.contract.yaml`.

## Was war

Jedes Laufzeitpaket trug dieselbe Adresse fest eingetragen:

```
https://192-168-68-78.k30068872219.direct.quickconnect.to:8443
```

Die NAS lag zu diesem Zeitpunkt auf `192.168.68.81` — nach einem Neustart am
selben Tag hatte DHCP ihr eine andere Adresse gegeben. Der Hostname bildet die
LAN-Adresse **in seinem eigenen Namen** ab, also zeigte er ins Leere.

## Gemessen

Namensauflösung:

```
k30068872219.direct.quickconnect.to                  46.114.41.133
192-168-68-81.k30068872219.direct.quickconnect.to    192.168.68.81
```

Der bloße Name ohne Adressteil zeigt auf die **öffentliche** Adresse — er wäre
also keine Abhilfe, sondern würde Busverkehr nach draußen und wieder herein
schicken.

Erreichbarkeit auf Port 8443:

```
.78 (Adresse im Repo)   connect: Connection refused   errno=61
.81 (NAS heute)         CONNECTED, subject=/CN=k30068872219.direct.quickconnect.to
                        Verify return code: 0 (ok)
```

Zertifikat, gelesen mit demselben `ssl.create_default_context()`, das
`bus_client.py` benutzt:

```
TLS ok, Protokoll: TLSv1.2
SAN: ['*.k30068872219.direct.quickconnect.to', 'k30068872219.direct.quickconnect.to']
```

**Der Platzhalter im Zertifikat ist der unangenehme Teil.** Er deckt *jede*
Adressvariante des Musters ab. Eine falsche Adresse fällt deshalb nie am
Zertifikat auf — sie fällt beim Verbinden auf, und das passiert erst im
Fenster.

Auf der neuen Adresse antwortet der Reverse Proxy, die Bus-Route ist wie
erwartet nicht veröffentlicht:

```
GET https://192-168-68-81.…:8443/bus/v1/status  →  HTTP 404 (nginx)
```

Das ist der Fail-closed-Zustand, kein Mangel: Die Proxy-Regel für die API wird
je Fenster geöffnet und danach zurückgenommen.

## Was daran die Fehlerklasse ist

Ein Name, der aus etwas Beweglichem zusammengesetzt ist und wie ein Bezeichner
aussieht — dieselbe Klasse wie `G-042` (Containername aus Projektordner,
Dienst und Index). Neu ist, warum es niemand sehen konnte:

- die lokalen Testsuiten laufen **absichtlich ohne Netz**
- das Deploy-Manifest vergleicht Prüfsummen, keine Adressen
- `nas_status.sh` fragte die API über `localhost` im Container, nie über die
  Adresse, die die Testpakete benutzen

Drei Wächter, und keiner konnte diese Frage stellen.

## Korrektur

Die Adresse steht jetzt als `BUS_BASE_URL` in `production_state.txt` und sonst
nirgends als Tatsache. Zwei Prüfungen, weil eine die Frage nicht beantworten
kann:

| | prüft | wo |
|---|---|---|
| `test_bus_address.py` | alle Vorkommen stimmen mit der einen Quelle überein | offline, überall lauffähig |
| `check_bus_address.sh` | die Adresse im Namen gehört **dieser** Maschine | auf der NAS, Gate in `nas_status.sh` |

Gegenprobe auf der NAS, mit der alten Adresse gefüttert:

```
=== mit der neuen Adresse (muss PASS sein) ===
im Namen steckt: 192.168.68.81
PASS: die Adresse gehoert dieser NAS
PASS: auf Port 8443 hoert jemand
RESULT: PASS
EXIT=0

=== Gegenprobe mit der alten Adresse (muss FAIL sein) ===
im Namen steckt: 192.168.68.78
FAIL: die Adresse gehoert dieser NAS nicht - eigene: 192.168.68.81 …
RESULT: FAIL (1)
EXIT=1
```

Und offline, mit einer einzelnen abweichenden Datei:

```
AssertionError: [] != ['workforce-agent/compose.contract.yaml: https://192-168-68-78.…:8443']
```

## Was offen bleibt

- **Die Adresse ist weiterhin eine Momentaufnahme.** Der CEO hat sie am
  2026-09-02 im Router reserviert; hält die Reservierung nicht oder zieht die
  NAS an den geplanten 5G-Router auf dem Dachboden, ändert sie sich wieder.
  Der Unterschied ist, dass es dann **auffällt**, statt im Fenster zu
  scheitern.
- **Kein Lauf hat die neue Adresse benutzt.** Belegt ist, dass TLS und
  Namensauflösung stimmen und der Proxy antwortet — nicht, dass ein Testpaket
  durchläuft. Das braucht das Fenster.
